- [x] 서버 측 핵심 지표 (HikariCP 사용/대기, CPU) 대시보드 표시, 실행 기록에 개발/실측 모드 구분
- **완료 기준**: 요청이 두 인스턴스로 나뉘는 것을 확인하고, `SYNCHRONIZED`가 개발 모드에서는 통과하고 실측 모드에서는 초과 발급되는 것을 재현 (시나리오 S7)
- **결과** (3,000명 동시, 재고 100): `SYNCHRONIZED`는 개발 모드(API 1대)에서 정확히 100장, 실측 모드(API 2대)에서 189~208장으로 초과 발급. 요청은 두 인스턴스에 50:50으로 나뉨
  - `SYNCHRONIZED`는 DB 커넥션 대기가 0이고 CPU만 100%. 요청이 DB 풀이 아니라 JVM 락 앞에서 줄을 선다
  - `DB_PESSIMISTIC`은 인스턴스마다 커넥션 10개를 다 쓰고 약 1,460개 요청이 커넥션을 기다림

- [x] `REDIS_LOCK` (Redisson, watchdog), `REDIS_ATOMIC` (Lua + 실패 시 보상, 키 유실 시 DB 기준 재적재)

- [x] 서버 멱등 처리: 같은 `X-Request-Id`의 재시도는 `IDEMPOTENT_REPLAY`로 성공 응답
- [x] 프론트: 사용자 그리드에 요청 횟수, 타임라인에 클릭·재시도 기록, 행동 모델 설정 UI, 응답·에러 사유 집계
- **완료 기준**: 10,000명 그리드가 끊기지 않고 갱신되고, `AGGRESSIVE`에서 재시도 폭주로 p99가 나빠지는 것 확인 (시나리오 S6)
- **결과** (실측 모드, 재고 100)
  - 5,000명 `IDEAL`: `REDIS_ATOMIC` 약 1,000~1,100 TPS · p99 4~5초, `DB_PESSIMISTIC` 약 200 TPS · p99 20초대, `REDIS_LOCK`은 락 대기 10초를 넘긴 요청이 대부분 `LOCK_TIMEOUT`. 세 전략 모두 초과·중복 발급 0
  - S3 (500명 × 5번 연타): 요청 2,500건 중 중복 응답 400건, DB 발급 100건으로 1인 1매 유지 (`REDIS_ATOMIC`, `DB_PESSIMISTIC` 모두)
  - S6 (`DB_PESSIMISTIC` 5,000명): 요청 수 `IDEAL` 5,000 → `REALISTIC` 15,603 → `AGGRESSIVE` 37,115(재시도 27,189). 에러로 끝난 사용자 690 → 2,040 → 2,960, p99 26.8초 → 29.9초. 클라이언트가 포기한 요청까지 서버가 처리하느라 쓸모 있는 처리량이 줄어든다
  - 10,000명 `REALISTIC` (`REDIS_ATOMIC`, 재고 1,000): 화면 메인 스레드 최대 정지 100ms로 그리드 갱신이 끊기지 않음. 동시 연결이 커널 대기 큐(4,096)를 넘쳐 4,594건이 연결 에러였지만 백오프+지터 재시도로 모두 회복
  - 부하를 걸면서 고친 실무형 문제: 메모리 한도에 붙은 컨테이너, 백프레셔 없는 Virtual Thread 서버의 OOM, nginx 워커 수 과다로 인한 OOM, 분산 락 lease 만료로 인한 초과 발급 1건 ([02 7장](02-architecture.md#7-인프라와-자원-제한-실측-모드), [03 REDIS_LOCK](03-issuance-strategies.md#5-redis_lock))

- [x] 매진되면 대기열을 닫고 기다리던 사용자에게 `SOLD_OUT` 통지
- [x] 행동 모델: 대기 중 새로고침(줄에서 나갔다가 맨 뒤로), 이탈(`ABANDONED`), 폴링 간격·흔들림
- [x] 프론트: 대기열 설정(초당 입장, SSE/폴링), 대기열 KPI·결과 집계, "직접 참여"를 실제 대기열에 연결, 미니 폰 뷰, 인스턴스별 힙
- **완료 기준**: 시뮬레이션 1만 명이 대기하는 중에 직접 참여해서, 가상 사용자들 뒤에 줄을 서고 순번이 줄어드는 모달 확인
- **결과** (실측 모드, `REDIS_ATOMIC`, 사용자 1만 명이 3초 동안 도착, 재고 3,000)
  - 직접 참여: 가상 사용자 약 6,800명 뒤에 줄을 서서 순번이 초당 약 100명씩 줄어드는 모달을 확인. 재고가 먼저 떨어져 대기 중에 매진 통지를 받음
  - 정합성: 모든 실행에서 정확히 3,000장, 초과·중복 0. 입장하지 못한 사용자는 줄에서 매진 통지를 받고 끝남 (발급 API까지 오지 않음)
  - 대기열이 서버를 지키는 효과: 초당 입장 100명이면 발급 지연 p50 94ms, 300명이면 4.5초. 입장 속도는 대기열을 돌리는 부하까지 감안한 처리량보다 낮게 잡아야 한다
  - SSE vs 폴링 (1만 명, 초당 입장 300명, `IDEAL`): SSE는 순번 확인 실패 0, 3,000장 모두 발급. 1초 폴링은 2만 8천 번 가까이 물어 API CPU가 100%에 붙고 순번 확인 7,787건이 실패(504), 1,863장만 발급되고 1,137장이 남음
  - `REALISTIC` (1만 명, 초당 100명): 대기 p50 15.5초, 2,300명 이탈, 291번 새로고침(맨 뒤로 다시 섬)
  - 부하를 걸면서 고친 문제 (자세한 내용은 [02 7장](02-architecture.md#7-인프라와-자원-제한-실측-모드))
    - **캐시 스탬피드**: 이벤트의 대기열 설정을 처음 읽을 때 DB에서 읽었더니, 1,000명이 동시에 캐시 미스를 내서 DB 커넥션 풀이 줄 서기 요청으로 꽉 참 (대기 272). Redis에 둔 설정을 읽게 바꿈
    - **SSE 연결 메모리**: 연결 하나에 힙 약 100KB(Tomcat 버퍼). 인스턴스당 5천 연결에서 힙 512MB가 OOM. coupon-api를 1.5G(힙 60%)로 올림
    - **SSE 푸시 CPU**: 1만 명 모두에게 1초마다 보내니 API CPU를 다 써서 발급이 느려짐. 곧 입장할 사람은 자주, 한참 남은 사람은 드물게 보내고(예상 대기의 10%, 1~5초) JSON을 직접 만들어 줄임
    - **연결 한도와 처리 동시성 분리**: SSE가 Tomcat 연결 한도(1000)를 다 차지해 발급 요청이 못 들어옴. 연결 한도는 1만으로 열고 발급만 벌크헤드(처리 1000 + 대기 2000, 넘치면 바로 503 `OVERLOADED`)로 제한. 대기 줄 길이를 안 정했을 때는 재시도 폭주에서 요청이 전부 서버 안에서 기다리며 nginx 연결을 다 잡아 새 연결을 못 받았음
    - **연결 대기 큐**: 1만 명이 몇 초 안에 SSE를 맺으면 API 컨테이너의 커널 연결 대기 큐(기본 4096)가 넘쳐 nginx가 연결하지 못함(504). `somaxconn`과 `accept-count`를 8192로
    - **nginx가 과부하를 장애로 오인**: 기본 `max_fails=1`이라 연결이 한 번 늦으면 인스턴스를 10초 빼고, 두 대가 다 빠져 모든 요청이 바로 502(`no live upstreams` 1만 5천 건). `max_fails=0`으로
    - **실시간 화면의 상태 누락**: 순번 갱신과 최종 상태가 거의 동시에 바뀌면, 화면에 보내는 쪽이 앞선 변경을 꺼낼 때 최종 상태가 아직 안 보여 옛 상태(대기 중)가 남는 경우가 있었음. 바뀐 사용자를 모두 꺼낸 뒤에 상태를 읽도록 고침
  - Phase 4 시나리오 다시 확인 (대기열 없이 `DB_PESSIMISTIC` 5,000명): `IDEAL` 에러 사용자 690 → 638, p99 26.8초 → 18.4초. `REALISTIC` 에러 사용자 2,040 → 1,022 (넘치는 요청을 바로 거절하니 클라이언트가 백오프하고 다시 성공). `AGGRESSIVE`는 3초 타임아웃에 즉시 재시도라 Phase 4 때도 실행마다 결과가 크게 달랐고(에러 사용자 2,960~4,998), 지금도 대부분 에러로 끝남

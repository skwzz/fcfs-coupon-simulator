# 01. 요구사항 & 시나리오

## 1. 목표

1. 선착순 쿠폰 발급 API를 **여러 동시성 전략**으로 구현한다.
2. N명의 가상 사용자가 동시에 발급을 요청하는 상황을 **재현할 수 있게** 한다.
3. 결과를 **정합성**(초과 발급, 중복 발급)과 **성능**(TPS, 지연시간) 기준으로 비교한다.
4. 개별 사용자가 겪는 흐름(요청 → 대기 → 입장 → 발급 성공/실패)을 **프론트엔드에서 눈으로** 확인한다.

## 2. 대표 시나리오

| # | 시나리오 | 재고 | 동시 사용자 | 확인할 것 |
|---|---|---|---|---|
| S1 | 락 없는 구현의 문제 확인 | 100 | 1,000 | 초과 발급이 실제로 발생하는지 |
| S2 | DB 락 vs Redis 비교 | 100 | 5,000 | 정합성은 같고 TPS와 p99가 얼마나 다른지 |
| S3 | 중복 요청 | 100 | 500명 × 각 5회 연타 | 1인 1매 제한이 지켜지는지 |
| S4 | 대기열 체험 | 1,000 | 10,000 | 순번이 줄어드는 모습, 입장 후 발급 |
| S5 | 비동기 발급 | 10,000 | 50,000 | 응답 속도와, DB 반영까지 걸리는 시간(Kafka lag) |
| S6 | 장애 주입 (선택) | 100 | 5,000 | Redis/Kafka 지연이나 중단 시 동작 |

## 3. 기능 요구사항

### 3.1 쿠폰 이벤트 관리
- 이벤트 생성: 이름, 총 수량, 시작 시각, 1인당 발급 한도(기본 1)
- 이벤트 초기화(reset): 발급 이력, Redis 재고, 대기열을 한 번에 비워서 같은 조건으로 다시 실행

### 3.2 쿠폰 발급
- `userId` 기준 1인 1매
- 재고가 소진되면 `SOLD_OUT` 응답
- 발급 전략을 요청마다 또는 이벤트마다 선택 ([03. 발급 전략](03-issuance-strategies.md))

### 3.3 대기열
- 대기열이 켜진 이벤트는 요청이 즉시 처리되지 않고 대기열에 들어간다.
- 사용자는 **내 순번**과 **예상 대기 시간**을 실시간으로 받는다.
- 서버는 초당 K명씩 입장을 허용하고, 입장한 사용자만 발급 API를 호출할 수 있다(입장 토큰).

### 3.4 시뮬레이션
- 프론트엔드에서 입력: 사용자 수 N, 재고, 전략, 대기열 사용 여부, 램프업(0초면 동시에), 1인당 요청 횟수
- 실행 중 실시간 지표와 사용자별 상태를 스트리밍
- 끝난 실행은 결과를 저장하고, 실행끼리 비교 가능

### 3.5 대시보드
- 실시간: 발급 수 / 남은 재고, TPS, 지연시간(p50/p95/p99), 결과별 건수(성공/매진/중복/에러), 대기열 길이
- 사용자 그리드: 가상 사용자 하나를 셀 하나로 표시하고 상태에 따라 색 변경
- 사용자 상세: 셀을 클릭하면 그 사용자의 타임라인(요청 → 대기 순번 변화 → 결과)
- 사후 검증: DB 기준 실제 발급 수, 초과 발급 건수, 중복 발급 건수

## 4. 비기능 요구사항

- **로컬 재현성**: `docker compose up` 한 번으로 인프라 전체 실행
- **정합성 검증은 DB 기준**: 화면 숫자가 아니라 실행이 끝난 뒤 DB를 쿼리해서 판정
- **목표 부하**: 로컬 노트북 기준 동시 사용자 10,000명 정도까지 실행 가능
- **측정 왜곡 인지**: 부하 생성기와 API 서버가 같은 머신이면 절대 수치보다 **전략 간 상대 비교**에 의미를 둔다.

## 5. 범위 밖

- 실제 회원가입/로그인 (userId는 시뮬레이터가 생성)
- 결제, 쿠폰 사용 처리
- 운영 배포 (로컬 Docker 환경까지만)
